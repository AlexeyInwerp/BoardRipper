# BoardRipper — Project Configuration

## Project Overview
BoardRipper — web-based PCB boardview file viewer and inspector. Hosted via Docker on NAS.

## License
AGPL-3.0. See [LICENSE](LICENSE) and [THIRD_PARTY.md](THIRD_PARTY.md). AGPL was

## Tech Stack
- **Rendering:** PixiJS v8 (WebGL) + pixi-viewport v6 (pan/zoom/culling/deceleration)
- **Frontend:** React 19 + TypeScript + Vite 7
- **Panels:** Dockview v5 (dockable, detachable, floating, popout-to-window)
- **Backend:** Go (net/http stdlib) — serves SPA, file management, board database, self-update
- **Container:** Docker (multi-stage build, scratch-based, ~15MB)
- **Tests:** Playwright (Chromium headless)

## Supported Formats
- **BVR1** — tab-delimited, absolute coords ×1000. Spec: `docs/formats/BVR_FORMAT.md`
- **BVR3** — keyword-value, relative pin coords. Spec: `docs/formats/BVR_FORMAT.md`
- **BRD** — binary obfuscated boardview (Apple/Mac repair). Spec: `docs/formats/BRD_FORMAT.md`
- **BDV** — plain-text boardview (BRDOUT/NETS/PARTS/PINS/NAILS sections). Spec: `docs/formats/BDV_FORMAT.md`
- **BDV ASC** — Honhan / Tebo-ICT multi-section ASC. Two deliveries of one document: obfuscated single-file `.bdv` (line-key cipher, three sections) and plain `.asc` section files, of which the older deliveries ship **five** — `format`/`nails`/`pins` plus `parts` (rotation + package name) and `nets` (net listing). Clicking any one of them in the Library opens the whole board: `asc-siblings.ts` groups same-folder files by the stem left after stripping the section keyword, and `asc-open.ts` merges them through the one code path the `.bdv` already uses. The OS picker and drag-drop can't see the folder, so a lone section opens as-is plus a toast whose "Add sections…" button takes the rest. Spec: `docs/formats/BDV_ASC_FORMAT.md`, design: `docs/specs/2026-08-09-asc-multi-file-open-design.md`
- **FZ** — ASUS boardview (RC6-encrypted, zlib-compressed). Spec: `docs/formats/FZ_FORMAT.md`
- **CAE** — ASRock PCBRepair Pro. Same container and cipher as FZ, different key; shares `parseFZ`, which probes a list of candidate keys. Unverified against real data (no sample). Spec: `docs/formats/FZ_FORMAT.md`
- **CAD** — GenCAD 1.4 text-based PCB interchange. `$ROUTES` arcs are CCW from `(x1,y1)` to `(x2,y2)`; the sweep is lifted into `[0, 2π)`, never clamped to ±π (issue #33 — the shortest-arc clamp drew major arcs as their complement and lost half of every two-record circle). Spec: `docs/formats/CAD_FORMAT.md`
- **XZZ** — XZZ PCB (DES-encrypted boardview). Arc block `0x01` is CCW from `angStart` to `angEnd`; the sweep is lifted into `[0, 360)`, never swapped-and-clamped to ≤180° (issue #33 — that shortest-arc rule turned every outline notch into an outward lobe). The plaintext tail past the `v6v6555v6v6` marker has **two encodings** and `parseXzzTailAnnotations` picks by content, not by file name: legacy `=<mV>=PART(pin)` records (diode values only, `… Middle layer diode value….pcb` companions), or — current iPhone-era deliveries — a JSON document after a **GB2312** banner (`{"part":[{"reference","alias","pad":[{"name","diode"}]}],"net":[…]}`) carrying diode readings **plus** the part- and net-rename tables XZZ's own viewer displays. JSON pad names are not `\d+`-only — BGA pads like `M7` are unrepresentable in the legacy grammar. Which of `reference`/`alias` the *binary* blocks use varies between deliveries of one board, so the diode join tries both keys and the rename only touches parts the binary named by `reference`; both renames refuse to merge two entities into one name (collision tested against existing names − names being vacated) and net renames run before `buildNets`, since net identity here **is** the string. A JSON tail can carry renames and no `pad[]` at all — that file genuinely has no diode data (iPhone16_16Plus ships exactly this pair: `AP+BB Boardview.pcb` 4750 readings, `AP+BB YiDianTong.pcb` none). **Board packs (v0.37.3+):** the file draws every board twice (top and bottom as separate layer-28 loops, side by side) and iPhone deliveries pack two or three boards into one file. `foldBoardPack` (`xzz-parser.ts`) + `parsers/xzz-boards.ts` classify the loops (board / cutout nested inside a board / fragment / frame), pair halves by a score on dimensions, gap and alignment (never an exact `segCount` key — a one-segment difference broke iPhone 5, a notch broke XS Max), fold **every** geometry kind of the bottom half onto the top (pins, part silk, silk, traces, vias, test pads, outline), slide the boards next to each other, and emit `BoardData.boards` + `Part.boardIndex`. **Which half is the top** comes from copper when the file has traces (a half's routed pins all sit on the first copper layer or all on the last, never mixed — the `PCB layer` deliveries) and otherwise from the exporter's layout rule: the left half (lower x) is the top, or the upper half for vertically stacked pairs. Verified on 78/78 trace-carrying corpus files, MacBook and iPhone alike; the old CPU rule (most-pinned part = top) is right on MacBooks and a coin flip on iPhone sandwich boards, so it is only logged (`CPU RULE DISAGREES`), never obeyed. The part header carries **no side field** (unk1 = flag, x, y, rotation; unk2 = a silkscreen label element) and OpenBoardView hard-codes Top, so there is nothing to decode. The file-wide mirror flip stays with the pin-direction detector, which now votes on folded boards with real sides (its false flip on the iPhone X Qualcomm pack came from mixed sides). The store's `deriveBoardView` only selects a board, undoes slide+fold for "Show all sides" (parts and outline only on packs) and applies the sidebar's per-board **Swap sides** override (persisted in file-view-prefs). Corpus, evidence and the phased plan: `docs/specs/2026-09-05-xzz-multi-board-unfold-review.md`. Spec: `docs/formats/XZZ_FORMAT.md`
- **TVW** — Teboview binary (multi-layer, traces, drill data). Spec: `docs/formats/TVW_FORMAT.md`
- **MENTOR_NEUTRAL** — Mentor Graphics Boardstation/Expedition neutral export (text, `.cad` extension; not GenCAD). Spec: `docs/formats/MENTOR_NEUTRAL_FORMAT.md`
- **ALLEGRO_BRD** — Cadence Allegro binary PCB. Two parser families share `parsers/allegro/`:
  - v16.x / v17.x / v18.x (magic `0x0013xxxx` / `0x0014xxxx` / `0x0015xxxx`) — original target. Spec: `docs/formats/ALLEGRO_BRD_FORMAT.md`
  - v15.x (magic `0x0012xxxx`) — added in v0.17.0 via blind RE; ~99% net coverage on 15.5.7 corpus, partial on 15.5.2. Spec: `docs/formats/ALLEGRO_V15_FORMAT.md`
- **ALTIUM_PCB** — Altium Designer / Circuit Maker / Circuit Studio binary `.PcbDoc` + PCB ASCII Version 5.0 text variant. CFB container (Designer 6.0+, 2005+). Phase 1: parts/pins/nets/outline. Spec: `docs/formats/ALTIUM_PCB_FORMAT.md`
- **KICAD** — KiCad `.kicad_pcb` (S-expression, KiCad 4–9). The only *openly specified* format we support, so the parser is an original implementation from KiCad's public docs, not a transliteration. Self-contained ~70-line tokenizer (`parseSExpr`, no deps, Node + browser); footprints→parts, pads→pins+pads, Edge.Cuts→outline, `(segment)`/`(arc)`→traces, `(via)`→vias. **Y is already down** so `flipY` stays false — unlike GenCAD/Allegro/XZZ/TVW. Angles are CCW-*as-displayed* over a Y-down frame, i.e. negative in raw coords; both the rotation sign and the "back-side footprints are already mirrored in the file" rule were settled empirically (place each pad, then require a track endpoint at that spot to carry that pad's net id — a position-only check can't tell the conventions apart on symmetric 2-pin chips). `Part.angleDeg`/`Pad.angleDeg` carry the raw-frame angle the renderer consumes; `meta.angleDeg` keeps the as-authored value for the Info panel. `gr_arc` stores `(start)(mid)(end)` — a real point ON the arc — so it is unambiguous and there is deliberately **no** shortest-arc normalisation (that idiom is issue #33, which bit `xzzArcSweepDeg` and `gencadArcSweepRad`). `(zone)`→`surfaces` (copper pours): KiCad stores the **computed** fill, one `(filled_polygon)` per island, so there's no fill algorithm — but three traps. (a) A zone with a `(keepout …)` child is a DRC rule area, **not copper**, and is skipped. An **unfilled** zone (no `(filled_polygon)`) is not drawn either: its `(polygon)` boundary is the pre-clearance outline and would paint solid copper over every foreign-net via — it is counted into `parserNotes` instead, as is a KiCad 4/5 `fill_segments` pour. (b) Never emit `(polygon)` alongside `(filled_polygon)` — double-draws the pour un-clipped. (c) The layer comes from the **island's** own `(layer …)`, not the zone's, which may be the layer-*set* shorthand `F&B.Cu` that names no single layer; an island whose layer is not copper (KiCad 6+ allows zones on mask/silk/user layers) is skipped, never defaulted onto F.Cu. The surface net follows the zone's `(net N)` id — `(net_name)` is a label KiCad refreshes only on re-fill and can be stale. **`Surface.voids` is never populated, and that is correct, not a shortcut:** KiCad stores fills *fractured* (`SHAPE_POLY_SET::Fracture()`) — cutouts are stitched into the outer ring by zero-width slits, so there is no hole list in the file. Measured, not assumed: 0 of 155 rings wind clockwise (no reversed inner rings), every duplicated vertex belongs to a backtracking pair, and — the decisive behavioural check — of 996 foreign-net vias that reach a fill's layer, **zero** test as inside the copper under the even-odd rule. The fractured ring is also what `drawSurface` wants (slit edges cancel, holes appear free), and `board-scene` explicitly refuses to punch `voids` at all on perf grounds. Edge.Cuts primitives are chained into contours by `chainPolylines` (10 mil join tolerance, NaN pen-up between contours; chaining is per primitive, not per sampled point) and `drawOutline` punches inner closed contours as holes with PixiJS `cut()` — v8 has no even-odd fill, so a cutout drawn as a plain second sub-path would be painted. Skipped: silkscreen, text, dimensions, custom-pad primitives, zones nested in footprints. Spec: `docs/formats/KICAD_PCB_FORMAT.md`
- **EAGLE_BRD** — Autodesk/CadSoft EAGLE 6.0+ XML `.brd` (third `.brd` claimant; XML sniff is disjoint from Apple BRD's and Allegro's binary magics, and it registers **after** Allegro so the extension-only fallback is unchanged). Pre-6.0 binary `.brd` is out of scope and rejected with a "re-save from EAGLE 6+" message. The format's whole difficulty is **indirection**: pin positions are not stored — `<element>` places a `<package>` by name and each pin is `package pad coords → R(a)·M → +(x,y)`, where `rot="[S][M]R<deg>"` mirrors across the local Y axis (→ bottom side) *before* rotating CCW; nets join by `(element, pad)` **name** via `<contactref>`, never by coordinate. Coordinates are always millimetres regardless of grid unit. Board outline is layer 20, searched in `<plain>` **and** inside placed packages (carrier/shield footprints often own the whole edge). `<wire curve="…">` is a signed CCW sweep and is used verbatim — never normalised to a shortest arc (issue #33). Verified by a routing oracle: on the fully-routed fixtures 100% of pins land exactly on a trace endpoint of their own net. Spec: `docs/formats/EAGLE_BRD_FORMAT.md`

## Key Architectural Decisions
- PixiJS v8 chosen over Canvas2D/Konva for GPU-accelerated rendering of 10,000+ components at 60fps
- `buildBoardScene()` in `renderer/board-scene.ts` is a shared pure function used by both `BoardRenderer` and `SettingsMockup` — visual changes propagate to both automatically
- BitmapText atlases for part/pin labels: dramatically fewer GPU draw calls vs per-label canvas Text objects
- Dockview chosen for IDE-like panel system with floating/popout window support
- Go backend chosen for minimal Docker footprint and single-binary deployment
- All format parsing happens client-side in TypeScript (no server dependency for rendering)
- `useSyncExternalStore` for reactive stores — getSnapshot must return a stable cached reference
- **NEVER call `app.destroy()` on PixiJS v8 Applications** — `destroy()` triggers `GlobalResourceRegistry.clear()` which corrupts the module-level `batchPool` in `Batcher.mjs`, permanently breaking ALL other Application instances with `_DefaultBatcher2.break: Cannot read properties of null`. Instead, just remove the canvas from DOM and let GC reclaim the Application + WebGL context. See `BoardRenderer.teardownForReinit()`.
- **NEVER `BitmapFont.uninstall()` on per-tab teardown.** `BitmapFont.install()` registers atlases in PixiJS's **global** registry — one atlas is shared by every open tab's `BitmapText`. Uninstalling on tab close / scene rebuild destroys the `TextureStyle` still referenced by other tabs, which later crashes in `GlTextureSystem.updateStyle → applyStyleParams` with `Cannot read properties of null (reading 'addressModeU')`. Atlases are content-keyed (`board-shadow-N-v3`, `board-pin-N`), idempotent, and safe to keep for the app lifetime.
- PDF panels use per-document state via `usePdfDoc(fileName)` hook, allowing multiple PDFs to render side-by-side. The singleton `pdfStore` tracks an "active" doc for mutations but each panel reads its own doc's state independently.
- **PDF render pipeline:** see [docs/PDF_VIEWER.md](docs/PDF_VIEWER.md) for the full architecture. Short summary: at zoom ≤ 1.05 a full-page path renders the current page to an `ImageBitmap` cache keyed by `(file, page, tier, cleanMode)`; above that a per-tile DOM-canvas path (`tile-manager.ts`) renders 1024×1024 tiles with an LRU cache keyed by `(file, page, col, row, scale)`. Both paths flow through `mainTierFromZoom → quantiseTier → hysteresisFilter → clampCanvasScale` before calling `page.render()`. A separate tier-1 preview cache provides instant backdrop on zoom/page transitions. Adjacent pages use `renderPageToBitmap` (capped at `maxAdjTier`). Quality presets in `QUALITY_CONFIGS` control tier caps, cache budgets, and settle delays.
- **PDF watermark filter (v0.30.3+):** parse-time string-matching filter implemented as a pdf.js patch in `src/frontend/patches/pdfjs-dist+<version>.patch`, applied by `patch-package` via the `postinstall` script. The patched worker examines each `showText` op's reconstructed glyph string against terms forwarded through a custom `watermarkFilter` render option and skips matching ops **before they enter the operator list**. Net effect: 5–10k watermark glyph runs per page never tokenised, streamed, or allocated; zero client-side callback overhead. Matching rule (NFKC-normalise → strip whitespace → lowercase → substring; NFKC decomposes ligatures like `ﬁ` so `"Vinaﬁx.com"` matches `"Vinafix"`) is kept in lock-step with `isPdfWatermarkText`/`normalizeForWatermark` in `render-settings.ts` (and `IsWatermark` in `pdfindex/watermark.go`, which imports `golang.org/x/text/unicode/norm`) so click-test and render-skip stay aligned by construction. Worker URL in `pdf-store.ts` points at the **unminified** `pdf.worker.mjs` because the patch targets readable source (Vite still minifies for prod). The earlier `operationsFilter`-callback approach (v0.4.2 – v0.30.2) was retired because pdf.js's `QueueOptimizer` reorders/merges ops between `getOperatorList` and `render`, so pre-computed indices didn't line up with what `render` actually executed on PDFs heavy enough to trigger the optimizer. See `src/frontend/patches/README.md` for the five-site edit recipe and the procedure to re-port the patch on `pdfjs-dist` version bumps.
- **PDF canvas rules:** Only **pooled offscreen** canvases (freshly acquired, used once, released) use `getContext('2d', { alpha: false })`. Persistent canvases (main visible canvas, adjacent page canvases, tile canvases) must NOT use `alpha: false` — resetting `canvas.width` doesn't reliably reset the alpha attribute across browsers, causing mirroring artifacts on reused canvases. Canvas pool (8 entries) shrinks backing store synchronously before pooling — never defer shrinking (race condition with reuse). Highlight, glyph, and tile canvases retain alpha.
- **Never pool pdf.js-rendered canvases.** After `page.render()` completes, the pdf.js Worker thread may still queue stale draw operations. Abandon the offscreen canvas to GC by setting `width = 1; height = 1` — do NOT return it to the canvas pool, or subsequent reuses will be corrupted with mirrored/flipped content.
- **Scroll modifier zoom speeds:** Both BoardViewer and PDF viewer support modifier-dependent zoom speeds: Shift+Scroll = slow zoom (precise), Ctrl+Scroll = fast zoom (coarse), trackpad pinch = direct proportional zoom. Ctrl and Cmd are **distinct keys** even on Mac — browsers emit `ctrlKey=true` wheel events for both physical Ctrl+Scroll and trackpad pinch, but the pinch gesture produces small deltaY values that map to proportional zoom, while Ctrl+mouse-wheel produces large deltaY steps. pixi-viewport natively lacks shift-key awareness, so `BoardRenderer.installShiftWheelHandler()` intercepts Shift+Scroll in capture phase. The speed difference comes from divisor constants: `/500` (shift, slow) vs `/200` (ctrl+wheel, fast). Do not unify these — the two-speed zoom is a deliberate feature.
- **PDF rotation + mirror + page modes:** Per-document `rotation` (0/90/180/270 CW), `mirror` (horizontal flip), and `pageMode` (`single` | `continuous`, default continuous) live in `pdf-store` (`PdfDocument`). **Rotation** is applied by passing `rotation: page.rotate + userRotation` to **every** `page.getViewport()` call in `PdfViewerPanel` (full-page, tiled, and adjacent paths) — pdf.js then swaps page dims for 90/270 so fit-width, `cssH`, the highlight/click transform (`viewportTransformRef`) and tile grid all adapt for free. Rotation does NOT key the bitmap/tile caches; instead a rotation-change effect clears `invalidatePageCache`/`invalidateTileCache` + adjacent canvases and re-fits (rotation is rare and deliberate). **Mirror** is a CSS `scaleX(-1)` baked into the wrapper transform by `applyTransform` (innermost, flipping around the committed-zoom content width via the `mirrorWidth()` helper) so the whole wrapper — page, tiles, highlight, overlays — flips together in all modes (full-page/tiled/continuous) with no cache or render changes; the only X-coordinate consumers that compensate are `hitTestWord` (`clickX = clientW - clickX`) and the two match-centering pans (`pan.x = clientW*(1-zoom) - pan.x`). Mirror is independent of rotation/page-mode and composes with both. **Effective single-page** (`pdfStore.isDocSinglePage`) = explicit single mode OR `rotation !== 0` — rotation forces single but **preserves** the user's `pageMode` so un-rotating restores continuous. Single-page = no adjacent-page rendering, no scroll/zoom page-flip (gated by `noFlip` in `handleWheel`), pan clamped to the current page (the `singlePage` branch in `clampPan`). Continuous = the original stacked-adjacent-pages + boundary-flip behaviour. Toolbar: the `pdf-rotate` (cycles CW) + `pdf-mirror` (toggle) + `pdf-page-mode` (toggle, disabled while rotated) group sits directly **right of the page-switching controls**. Shortcuts (PDF panel active): `rotateBoardCW/CCW` (Q/E) and `rotateCW/CCW` (⌘←/→) rotate; `mirrorBoard` (⌘↑) mirrors — all previously no-op on PDF. E2E: `tests/pdf-rotation.spec.ts`.
- **Secure update pipeline (v0.19.0+):** Releases are signed offline by the maintainer (Ed25519/minisign); the running container's compiled-in trusted key set verifies every manifest before any I/O on its body. `PubKey` (build-arg `PUBKEY`) is the primary signer; `PubKeys` (build-arg `PUBKEYS`, comma-separated) holds additional keys for a **rotation overlap window** — `TrustedKeys()` merges them and `VerifyManifestAny` accepts a signature verifying under any one, which is what lets a key rotation ship through the normal update path instead of stranding every install. Both are ldflags with **no env/file override**; an empty set fails closed. Rotation procedure: `docs/RELEASE_RUNBOOK.md` ▸ "Rotating the signing key". Two **manifest** sources walked in order — `https://www.ripperdoc.de/boardripper/` (canonical) and `https://github.com/AlexeyInwerp/BoardRipper/releases/latest/download` (fallback; the release carries `manifest.json` + `.minisig` + tarball as assets) — first whose signature verifies wins. GHCR is *not* a manifest source: it is an OCI registry and cannot serve `/manifest.json`; it remains where the image itself is pulled from, by digest. Serving the manifest from GitHub grants GitHub no trust — a tampered copy fails `VerifyManifestAny` exactly as a tampered mirror would. The tarball additionally lists the GitHub release asset in `url_mirrors`, which `Apply` already walks after `url_primary`. Manifest schema includes monotonic `counter` (replay defence), `released_at` + `not_after` (30-day freshness window + 90-day expiry — see freshness invariants below), `min_supported_version` (downgrade defence), `important` flag (red-banner UX) + `important_reason` + `notes_url`, image registry/tag/digest, tarball sha256 + `size_bytes`, and `orchestrator_image_digest` (the multi-arch INDEX digest of the alpine container that swaps the running image). `/api/update/*` is gated by a per-install 32-byte secret persisted at `/data/.update-secret` (mode 0600); the install's monotonic counter persists alongside at `/data/.update-counter`. Cookie attributes: HttpOnly + SameSite=Strict + conditional Secure based on request scheme. Healthcheck-based rollback: orchestrator polls the new container's IP-resolved `/api/health` for 60 s and reverts on failure. The previous image is tagged `boardripper:previous` before swap so a manual rollback is one `docker run` away. Drop-to-update bundle (`POST /api/update/apply-bundle`) is the recovery escape-hatch — a signed-manifest+tarball single file the user can drag onto the window when GHCR + ripperdoc.de are both unreachable. Same trust envelope as the network path. **Operational invariants:** download timeout 10 min, body cap = manifest's `size_bytes` (or 1 GiB fallback), `released_at` rejection bounds [now − 30d, now + 24h], single-flight gate prevents concurrent `Apply` / `ApplyBundle`. See `docs/RELEASE_RUNBOOK.md`.
- **Release network path:** the FTP credential lives in two files — `~/.config/boardripper/release.env` (release.sh) and `RipperDocWeb/ftp.env` (deploy.sh) — rotate both. `lftp` retried a stale password until fail2ban blocked the releasing Mac's IP for ~2 h (2026-09-03); both scripts now ping/TCP-probe `ftp.ripperdoc.de:21` before sending a credential and cap the login at one retry. Verify a credential from another IP with `scripts/ftp-check.sh --via rd-nas` (runs lftp on the NAS over Tailscale, password on stdin). If this machine is blocked, `release.sh … --via-tailscale [rd-nas]` routes the run through a Tailscale exit node and clears it on exit. Never probe FTP anonymously while diagnosing — a ban vs. a bad password is told apart by whether port **443** on the same host connects. Runbook: "FTP: credentials, bans, and the Tailscale route".

- **HDR selection outline (experimental, opt-in, default OFF):** on an HDR display the **selected part's outline** — the same shape `drawPartOutline` already strokes — burns **above SDR white** for as long as it stays selected: a "super-selection" that cannot be confused with the thousands of SDR-white neighbours on a dense board. It is the existing selection outline, lit; **not** a halo or glow blob behind the part (an early iteration drew a radial blob — wrong shape, corrected 2026-08-04). Implemented as a DOM layer (`renderer/hdr-selection-outline.ts`, `zIndex:3`, a `containerEl` sibling above the label overlay): one thin rotated `<div>` per polygon edge, each stretching a solid PQ-encoded AVIF tile, which is how an *image*-only technique can draw an arbitrary polygon outline (OBB, AABB, or a 24-gon for single-pin parts — mirroring `drawPartOutline`'s shape choice exactly so the HDR line sits ON the SDR one). Thickness matches the SDR primary stroke (`selectionWidth * 1.7`, 2px floor). **Not** the WebGPU `rgba16float` route: WebGL has no shipped HDR path, Canvas2D is 8-bit, Pixi clamps vertex colours to 8-bit and hardcodes `bgra8unorm`, and WebGPU-HDR is Chromium-only. HDR *images* are the only technique honoured by both Chrome and Safari — the cost is that all HDR geometry must be composed of stretched image tiles (straight edges, solid fills); no per-pixel shading, gradients, or HDR text. PNG `cICP` was rejected: Safari does not map it to EDR. **Measured on real hardware via `/hdr-probe.html`, not inferred from specs (which were wrong twice):** a PQ sprite keeps its headroom composited over a WebGL canvas ✓, but **opacity compositing flattens HDR back to SDR** ✗ — so brightness is NEVER an alpha, and equally never a CSS mask or `filter: brightness()`. Instead `scripts/make-hdr-glow.ts` (maintainer tool; `avifenc` is absent from CI and the image, so the assets are committed) bakes a **24-rung luminance ladder** of solid tiles `hdr-line-<0..23>.avif`, 4000→200 nits, ~0.19 stops apart, ~7 KB total; `hdrGlowIntensity` (1–10) selects a rung via `rungForIntensity()`. Gated on `renderSettings.hdrFocusGlow` **and** live `matchMedia('(dynamic-range: high)')`, so undocking to an SDR monitor tears the layer down on the next frame. Reads `boardStore.selection` directly rather than a parallel focus-target field — **the feature makes zero changes to `board-store.ts` and is purely additive, so it cannot regress existing selection**; the SDR highlight is untouched, which is the entire SDR fallback story. Focus target only (never net members, never all hits — headroom is a shared budget that collapses under large lit areas). `focusHaloGeometry()` (`renderer/focus-halo.ts`) remains the dark spotlight's shared sizing rule, extracted in the same work. Switches: Settings ▸ Selection & Highlight (stays visible-but-hinted on SDR) and the start page card under Interface scale (always shown; the readout is the detection result and a two-board mockup draws the outline with the real PQ tiles at the slider's rung, so the user sees whether this screen has headroom). The earlier "Your monitor supports HDR / Don't show again" discovery prompt was retired 2026-09-05. Known open risk: a *steady* bright source is what makes macOS re-tone-map — if surrounding UI dims, lower the rung. Spec: `docs/specs/2026-08-04-hdr-focus-glow-design.md`, plan `docs/plans/2026-08-04-hdr-focus-glow.md`.

Pin scaling hardening: `computeGridSize` refines the pin-batching grid by `pinSizeScale` and `flushChunked`'s pad budget divides by it, both keeping per-Graphics vertices under the uint16 index ceiling when pins are enlarged. **Two crash fixes shipped with it** (both were latent, surfaced by rebuild-on-settings-change): (1) the selection **halo sprite** is persistent but mounted into `scene.root`, yet `invalidateAllScenes` detached every *other* persistent overlay before `destroy({children:true})` — now it detaches the halo too (+ `updateHalo` self-heals a destroyed sprite); regression `tests/halo-rebuild-regression.spec.ts`. (2) The uint16 vertex-ceiling guards above. **Component-name fade:** in the Canvas2D label overlay, `part` labels fade toward a 0.14 ghost as their on-screen size grows (`partNameFade`, smoothstep 80→240px) so a big BGA designator stops blanketing the net names underneath (net names are drawn earlier, pins are on the WebGL canvas below the overlay — the fade reveals both without a z-reorder). Related UI (same branch): Settings tab strip is now icon-based (Tabler icons, `library-tab` styling) and responsively expands labels to fit / collapses to icons via a ResizeObserver; the settings search bar moved below the tabs; Library's **Donor boards** is now a sub-item of the **PDF** tab (mirrors the Folders source-menu dropdown).

## Safety Rules
- **COMMIT before removing code.** Before deleting or replacing any significant block of code (>10 lines), commit the current working state first. A stray `git checkout` must never destroy hours of work.
- **COMMIT at milestones.** When a feature, phase, or significant progress is complete and building, commit immediately — don't accumulate uncommitted work.

## Conventions
- TypeScript strict mode
- All coordinates internally in mils (thousandths of an inch)
- Component naming: PascalCase for React components, camelCase for functions/variables
- File format parsers are pure functions: `(buffer: ArrayBuffer) => BoardData | Promise<BoardData>` (see `FormatDescriptor.parse` in `parsers/registry.ts`)
- **Logging:** Use scoped loggers from `store/log-store.ts` — never raw `console.log`. Import `{ log }` and use `log.parser.*`, `log.render.*`, `log.pdf.*`, `log.scan.*`, `log.ui.*`, `log.cache.*`, `log.perf.*`, `log.update.*`, `log.obd.*`, `log.cloud.*`. The Debug Panel filters by scope. Avoid logging in hot paths (per-frame, per-pointer-move).

## Public landing page (`landing/`)
The `landing/` folder owns the static page served at <https://www.ripperdoc.de/boardripper/>. It is plain HTML5 with embedded CSS — no JS, no build step, not part of any application build. To update the page (new feature, new screenshot, format-table change): edit `landing/index.html` directly and replace screenshots in `landing/screenshots/`. The RipperDocWeb deploy script rsyncs this folder; nothing in this repo's build pipeline is involved. See `landing/README.md` for the full update workflow.
