The toolbar, three ways

What is on the top bar today, what is wrong with it, and three directions drawn in the app's own chrome. C is the recommendation; A is the safe first step toward it, B is what "one icon language" looks like if you want the toolbar to match the rail.

Today as shipped in v0.38.0

Global search…
dev
  • Three icon languages in one bar. Tabler icons (sidebar, upload, butterfly), Unicode arrows (⇅ ↺ ↻ ⇔ ⇕) and text ("2 window mode", "Top", "180°"). The arrows render differently per OS font and never match the icon weight next to them.
  • Each group is a boxed inset. Three dark boxes with borders make a 40px bar read heavy, and the boxes do not say what the groups mean.
  • A rare action owns the widest button. "2 window mode" is used once a session at most; it sits first, labelled, beside Upload.
  • The most-used control is buried in the middle. Top / Bottom is what a repair session toggles all day; it sits between file actions and transforms, with a cryptic ⇅ between the two words.
  • App-level and board-level controls are mixed. Sidebar, Upload, search, version are about the app. Side, rotate, mirror, traces are about this board — and change per tab. Nothing in the bar says which is which.
  • Right half is empty. Search stops mid-bar; info and version float at the far right.

A Quiet groups, one icon language

  Search parts, nets, PDFs, library…
dev
  • Same order, same reach, half the noise. Boxes become hairline separators; every glyph becomes a Tabler icon at one weight.
  • Top / Bottom is a real segmented control with a caret for the rare options (flip axis, butterfly, show both). The ⇅ mystery button goes away.
  • Rotate keeps two buttons; the rest moves into a "more" menu (180°, mirror H/V, traces). Five transform buttons were four too many for how often mirror is used.
  • Search is centred and says what it searches. 2-window mode moves to the right cluster as an icon; it is a window action, not a file action.
  • Risk: lowest. Nothing moves between surfaces, so every existing shortcut and test still applies. It does not fix the app-vs-board mixing.

B Captioned, the rail's language

Search parts, nets, PDFs, library…
dev
  • The whole app speaks one language. Rail, panel tabs and toolbar all use icon-over-caption cells. New users never have to hover to find out what a glyph does.
  • Costs 12px of height (40 → 52) on a tool where the board is the product. The rail already spent 46px of width for the same reason; you may not want to spend both.
  • Captions under "Rotate ↺ / ↻" show the limit of the idea: some actions do not have a one-word name, and a caption that needs a glyph is not helping.
  • Risk: medium. Layout change only, no behaviour change, but every toolbar test that reads button text needs the same attribute migration the rail got.

C Split: the bar is for the app, the board's bar is for the board● recommended

  • The top bar becomes the app's bar: sidebar, Open, search, window mode, about, version. Six things, stable across tabs, plenty of room.
  • Side, rotate, mirror and traces move down into the board's own control bar — the one that is already per-tab, already sits on the board it changes, and since today folds away with one click. Switching tabs no longer leaves a Top/Bottom state in the toolbar that belongs to a different board.
  • "Nothing but the board" becomes real: cycle the sidebar out, fold the shade, and only the app bar is left. With A or B the transforms stay on screen whatever you do.
  • Search gets the centre and the width it deserves. It is the one control that spans board, PDFs and library.
  • Risk: highest of the three, but contained: the transforms already exist as store actions, the overlay already has a slot registry and a drag-to-arrange Settings editor, so each moved control is a new slot, not new behaviour. Keyboard shortcuts are unchanged. Tests that click the toolbar's Top/Bottom need to click the slot instead.

Why the overlay bar and not a second toolbar row. The overlay is already the board's control surface: per-tab, on the board, slot-based, user-arrangeable in Settings, and now collapsible. Adding the transforms there is adding slots. A second row would be a fourth permanent horizontal strip.

What stays exactly as is. Every store action (boardStore.rotateCW, selectTop, …), every keyboard shortcut, the shift-to-peek gesture on Top/Bottom, the hold-to-peek tooltip text. Only the button's home changes.

Sequencing if you want it in steps. A first (one afternoon, no behaviour change), then C's move of Top/Bottom alone (the control people touch most), then the rest of the transforms once the segmented slot has been used for a while.

Open question. With C, a PDF tab shows a nearly empty top bar. That is arguably correct — a PDF has its own controls in its panel — but it is worth seeing on a real screen before deciding.
