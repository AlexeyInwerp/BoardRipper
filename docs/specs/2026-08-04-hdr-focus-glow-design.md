# HDR focus glow — brighter-than-white highlights on search/lookup/selection

**Date:** 2026-08-04 · **Status:** approved (user-confirmed in session)
**Problem owner:** bench users on HDR-capable displays who lose the found part in a dense board.

## Problem

Three navigation flows land the user on a specific thing and must say *here it is*:

- **search** — stepping through result hits (`searchIndices`, `BoardRenderer.ts:3960`)
- **PDF → board lookup** — landing on a part resolved from a schematic
- **selection stepping** — walking a net or a part's pins across components

All three converge on one place: the selection pass in `renderSelection()`
(`BoardRenderer.ts:3960–4074`) — `selectionGfx` fills/strokes plus the `activeNets` glow
list, over an ambient-dim rect. That pass has exactly three tools: **hue**, **alpha**, and
**darkening everything else**. `0xffffff` at alpha 1.0 is the ceiling, and on a dense BGA
under dim mode the found pin still competes with a few thousand SDR-white neighbours.

HDR displays have headroom above SDR white that the board canvas never touches. Spending a
little of it on the *one* thing the user just navigated to is a signal that cannot be
confused with anything else on screen, because nothing else on screen can produce it.

Scope decisions taken in the design session:

- **Audience:** anything that can do it — Chrome *and* Safari, graceful SDR fallback
  everywhere else. (Rules out the Chromium-only WebGPU route as the primary path.)
- **Glow scope:** the **focus target only** — the current search hit, the lookup target,
  the selected part/pin. Never net members, never all hits.
- **Timing:** **steady while focused** — a persistent "super-selection" that holds for as
  long as the target is selected, not a flash. (Revised 2026-08-04 after seeing the probe:
  the original design said pulse-then-fade. A steady glow is what the navigation flows
  actually want, and it removes the fade mechanism entirely.)

## Background: what HDR is actually reachable from a browser (Aug 2026)

| Path | Status | Usable |
|---|---|---|
| WebGL `drawingBufferStorage(RGBA16F)` + `drawingBufferToneMapping({mode:'extended'})` | explainer/proposal, **not shipped** | ✗ — and WebGL is our default renderer |
| WebGPU `context.configure({format:'rgba16float', toneMapping:{mode:'extended'}})` | shipped Chrome 129+ | ✗ as primary — Chromium-only |
| Canvas2D | 8-bit by spec | ✗ — rules out a canvas overlay |
| CSS HDR colours (`color(rec2100-pq …)` above white) | draft, not shipped | ✗ |
| **HDR images** (Rec.2100 PQ ICC profile / AVIF gain map) | honored by Chrome, Safari, macOS/iOS | ✓ **chosen** |
| `dynamic-range-limit`, `@media (dynamic-range: high)` | Chrome 136+ / Safari 26+ | ✓ for gating |

Two blockers that would apply to the WebGPU route, recorded so the decision isn't
re-litigated later:

1. PixiJS v8.17 hardcodes `format: "bgra8unorm"` with no `toneMapping` in
   `GpuRenderTargetAdaptor.mjs:171` — it would need a patch-package patch. (That *is*
   viable now: `patches/` lands before `npm ci` in `Dockerfile:5`, unlike the old
   watermark-patch situation where patches never reached the image.)
2. An HDR backbuffer alone changes nothing. Pixi's batch shader takes vertex colours as
   8-bit, so everything is clamped to 1.0 long before it reaches the buffer. The highlight
   geometry would need its own shader emitting > 1.0.

The chosen image path avoids both, at the cost of only being able to draw **soft blobs** —
no HDR outlines, strokes, or net lines.

## Design

### Overlay layer

New `src/frontend/src/renderer/hdr-glow-overlay.ts`, class `HdrGlowOverlay`, modelled
directly on `LabelOverlay` (`label-overlay.ts`): same lifecycle (`resize`,
`setCssTransform`, `destroy`), same container, mounted one layer above it.

It owns a single absolutely-positioned `<div>`:

- `pointer-events: none` — pins under the glow radius must stay selectable, same rule the
  existing halo sprite follows (`spr.eventMode = 'none'`).
- `dynamic-range-limit: no-limit`.
- `background-image` = a pre-baked 256×256 radial white gradient **AVIF tagged CICP 9/16/0**
  (BT.2020 primaries, SMPTE ST 2084 PQ transfer, identity matrix). Not a canvas — Canvas2D
  is 8-bit and would defeat the technique. Not PNG: Safari does not map PNG `cICP` to EDR,
  and Safari is half the chosen audience.

The assets ship as `src/frontend/public/hdr-glow-<0..23>.avif` — a 24-rung luminance ladder
from 4000 down to 200 nits, geometrically spaced (~0.19 stops per rung), ~1.2 KB each and
~27 KB total. `hdr-glow.avif` is rung 0 under a stable name. All are generated by
`scripts/make-hdr-glow.ts` so the encoding is reproducible rather than an unexplained binary
in the tree; that script is a **maintainer tool** (`avifenc` is absent from CI and the Docker
image), so the `.avif` files are committed.

### Capability gating

- `matchMedia('(dynamic-range: high)')` with a **live** listener — plugging in a display,
  or macOS/iOS battery saver forcing the panel to SDR, flips the query and the overlay
  mounts or unmounts to match.
- Setting `hdrFocusGlow` in `render-settings.ts`, **default off**, labelled
  `(experimental)` per the standing opt-in convention for new render modes.
- Setting `hdrGlowIntensity` selects a **rung on the baked luminance ladder**. Alpha is not
  available: opacity compositing flattens HDR back to SDR (measured, see Findings), so the
  only way to vary brightness is to show a sprite baked at a different peak luminance.
- Both are **global** settings (`renderSettingsStore.globalSettings`, edited via
  `updateGlobal`), alongside `textFastMode` and `dragToZoom` — not per-tab draft settings.
  This is a property of the user's display, not of a board, so it must not vary per tab.
- Not capable, or setting off → the overlay never mounts. Zero cost.

### Where the switch lives

Two surfaces, both bound to the same global setting so they stay in lock-step:

- **Settings ▸ Selection & Highlight** (`SettingsPanel.tsx:2360`) — a `Toggle` "HDR focus
  glow (experimental)" plus a `Slider` "HDR Glow Intensity" (rung selector), using the
  existing section primitives. This section already owns every other highlight control
  (selection fill, net highlight ring, dim overlay), so the glow belongs with them rather
  than in Performance & Debug.
- **Start page** (`HomeBackdrop.tsx`) — a `home-toggle-row` entry following the existing
  `AutoSwitchToggle` / `AutoOpenPdfToggle` shape, so the feature is reachable without
  opening Settings.

Behaviour when the display is not HDR-capable is deliberately **different** between the two:

- The start-page row is **hidden**. The home screen is a dashboard of things you can act
  on, not a settings dump; a permanently dead row is noise.
- The Settings toggle stays **visible but disabled**, with a title explaining that no HDR
  display was detected. A user who enabled this on a laptop and later docked to an SDR
  monitor needs to see *why* it stopped working — silently hiding the control would read as
  a bug.

**The existing SDR highlight is untouched in every case.** HDR is strictly additive on top,
never a replacement. This is what makes the fallback free and the failure mode benign: on
an SDR display the feature is simply absent, and nothing about the current highlight
changes.

### Trigger: the focus target

One new store concept — `boardStore.focusTarget = { partIndex: number; pinIndex: number | null }
| null` — set at the existing call sites that land the user somewhere: search step (next/prev
hit), PDF→board lookup, and selection stepping. `pinIndex` is `null` when the focus is a whole
part rather than a specific pin; the glow then centres on the part and sizes from its outline.
Cleared when the selection is cleared.

Each frame `BoardRenderer` reads `focusTarget` and, when set:

1. computes the target's world position and radius,
2. projects to screen space using the same matrix `LabelOverlay` already uses — so rotate,
   mirror, and butterfly work for free,
3. positions the sprite. There is no animation and no clock — the glow simply tracks the
   focus target, so it costs nothing beyond a transform update on frames that already run.

### Shared geometry

The sizing math currently living inside `updateHalo()` (`BoardRenderer.ts:3660`) — additive
growth rather than multiplicative, 1500-mil floor so tiny passives still get a generous
radius, fixed padding so a large BGA doesn't scale out into the next county — is
**extracted** into a pure `focusHaloGeometry(part, pin)`.

Both the existing dark spotlight and the new bright glow consume it. They then cannot drift
apart, and the math becomes unit-testable in isolation.

## Findings (probe, 2026-08-04, real HDR hardware)

Measured with `hdr-probe.html`, not inferred from specifications — which were wrong twice
here, so nothing below should be re-derived from documentation:

1. **A PQ AVIF reaches display headroom standalone** (swatch 2 out-glows plain white).
2. **It keeps that headroom composited over a WebGL canvas** (swatch 3 == swatch 2). This is
   the load-bearing result: it is what makes a DOM overlay above the Pixi canvas viable, and
   it is the reason this design proceeds rather than falling back to WebGPU.
3. **Opacity flattens HDR to SDR** (swatch 4 == plain white). Alpha is therefore unusable for
   anything — fading, intensity, or dimming. Brightness can only be varied by swapping to a
   sprite baked at a different peak luminance.
4. **WebGPU extended tone mapping works on the same display** (swatch 5, brightest). Recorded
   as the fallback route's viability, not as the chosen path.
5. **A 7-rung ladder steps visibly**; 24 rungs (~0.19 stops each) was the response. Only
   relevant now as the intensity scale, since the steady design does not animate.

## Testing

### The probe is a gate, not a nice-to-have

`src/frontend/public/hdr-probe.html`, mirroring the existing `webgl-probe.html` pattern.
Reports `dynamic-range` and `color-gamut`, then renders five swatches side by side:

1. plain white div (SDR reference)
2. PQ-ICC image standalone
3. **same image layered over a WebGL canvas**
4. **same, at opacity < 1**
5. WebGPU extended-toneMapping square, for reference

Swatches 3 and 4 answer the one question no specification does: whether DOM compositing
over a canvas — and compositing with opacity, which the pulse requires — preserves display
headroom or silently tone-maps back to SDR. Browsers flatten HDR in exactly these
situations often enough that this must be verified before any renderer code is written.

**Resolved:** 3 held, 4 flattened. Swatch 3 is the one the design depended on, so the route
stands; swatch 4 killed alpha as a mechanism, which the steady design no longer needs. The
probe's second row now serves the remaining open question — which luminance rung is the
right default intensity.

Afterwards the probe doubles as the diagnostic for "HDR does nothing on my machine"
reports, the same role `webgl-probe.html` plays today.

### Automated

- Unit tests for the pulse envelope and `focusHaloGeometry` — pure functions, following the
  `label-overlay.test.ts` / `smooth-zoom.test.ts` precedent.
- Playwright asserts **structure only**: the overlay mounts when capable + enabled, does
  not when either is false, is positioned at the focus target's screen coordinates, and
  decays to zero opacity. Headless Chromium cannot verify headroom.

Real visual confirmation is the user's, on real hardware, per the standing convention that
the user controls visual verification.

## Out of scope (YAGNI)

- HDR on net members or on all search hits — focus target only, by decision.
- HDR net lines, outlines, or strokes. The image technique produces soft blobs; hard-edged
  arbitrary pad geometry is not reachable this way.
- The WebGPU backbuffer route (see Background for why, and what it would cost).
- Per-theme HDR tints. White only.

## Risks

1. ~~**Compositing flattening.**~~ Resolved by the probe: the sprite keeps its headroom over
   a canvas. Alpha does not survive compositing, which is why intensity is a rung selector
   rather than an opacity.
2. **Windows** requires system-wide HDR, which washes out the surrounding desktop and UI.
   The media query reports honestly so users self-select, but expect occasional "why is
   everything grey now" reports.
3. **Headroom drift — now the main open risk.** A *steady* bright source is exactly what
   makes macOS re-tone-map the scene, and the design moved from a brief pulse to a persistent
   glow at the user's direction after hands-on review. If the surrounding UI visibly dims
   while a part is selected, the mitigation is a lower default rung, not a return to the
   pulse. Worth watching during the field-debug window.
